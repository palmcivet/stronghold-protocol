## 工程优化

### 拆分静态资源

目前有几个 Issue 提到了资源下载相关的问题：#106、#141、#151 。采用编译手段之后，可以更灵活地分析和输出产物。

- 前后端分离，静态资源从公共 CDN 拉取，减轻部署服务器的压力
- 前端构建为静态站点，用 NGINX 独立部署。对局进程只保留对局和 WebSocket，更换页面不重启房间
- 前端资源设置缓存，可以避免重复下载
- 引入 PWA 或者资源包等手段，可以提前下载好数据，避免运行时加载
- 使用静态资源封装客户端

社区虽然发达，但是没有一个项目能够把所需的资源都拿到。

字体可以使用前端技术栈来解决，理论上 mod 不会重载字体

- 本地开发和 CI 中，初始化脚本从社区库提取数据
    - git shallow clone 或者只拉取某些资源，放在 .cache，下次执行有就不下载
    - 本地开发时，如果存在客户端，则单独提取数据，使用 ArkUnpacker.exe。避免引入 Python（优化手段）
        - 现在的本机提取是 UnityPy 脚本；替代方案包括 TS 直接读取 Unity AssetBundle、ArkUnpacker（同为 Python 栈）及其他工具
        - 评估 macOS、Linux、Windows 与 iOS 客户端（ASTC 图集页）的可用性，LZ4AK 解码，网格、材质参数与 prefab 变换的导出，以及维护成本
        - 替换后只换本机提取来源的实现，原始目录、需求清单与包清单不变
- assets-catalog 理念不变
    - `/compiler` 只提供工具库
    - 只关注通用的数据。干员、敌人、语音等数据都来自官方，放到哪里都是统一的
- alliance/data
    - `/compiler` 提取出该 app 所需的资源
    - `/` 运行时解析器、加载器
- 部署时
    - 前端资源
        - 只通过后端接口耦合，由用户指定后端地址
        - 连接后和后端协商，协商内容包括前端资源、基础数据包
        - nginx 或 GitHub Pages 等 CDN
    - 基础数据包
        - 可使用官方版本作为发行版本号，只被前端使用
        - 只通过资源句柄耦合，句柄来自声明文件，不写死代码
        - 使用声明文件的版本号来协商版本
    - 赛季数据包
        - 客户端和服务端都会使用
        - 后端服务一次只启用一个赛季
        - 后端服务和赛季包独立，停机更换赛季包，指定文件地址

开发阶段使用 vite 插件能解决。等所有模块完备后再决策。需要定义 manifest 的格式
